# Differential testing of IVXV (Estonia)

Verdict comparison between Estonia's IVXV (`https://github.com/valimised/ivxv`,
branch `published`, commit `2785872f84dffb56bbecc41b096a7ee0f2876e64`,
KOV2025, apps 1.10.3), Verificatum's `vmnv` 3.1.0 and the certified verifiers
of this repository, on inputs we generate. No attack against IVXV is built:
an unexpected acceptance is recorded and the missing check identified.

IVXV is licensed CC BY-NC-ND 3.0 (© Estonian State Electoral Office). The
harness fetches the pinned commit at run time, checks that the checkout is
unmodified, and compiles our own drivers (`java/`, `go/`) alongside it; no
IVXV file is copied into this repository or changed.

## Reproducing

```sh
bench/ivxv-diff/run.sh [WORK]        # SEED=1 JOBS=4; WORK defaults to bench/ivxv-diff/_work
```

Requirements (macOS, Homebrew): `openjdk@21` (IVXV, Gradle 8.11),
`openjdk@25` (Verificatum), `go` (1.27.3 used, `GOTOOLCHAIN=local`), the
default opam switch (Rocq, dune, cryptokit, yojson), python3, git, curl,
make. `run.sh`:

1. clones IVXV and checks out the pinned commit (verified, unmodified);
2. downloads Gradle 8.11 (sha256 `57dafb5c…f1e9`) and builds IVXV's auditor
   (`installDist`, dependencies from Maven Central);
3. downloads Verificatum 3.1.0 (sha256 `e848b870…3aad`) and builds `vcr` and
   `vmn` as `bench/verificatum-diff` does; checks that `group.txt` is
   `vog -gen ModPGroup -fixed 2048` (the safe-prime group of the campaign);
4. builds the Go driver against the checkout's `core/` (a `replace`
   directive) and checks that RFC 3526 group 14 equals the library's table;
5. regenerates the certified instances (`mkins.py`) and builds
   `src/Executable/Ivxvdiff/main.exe`;
6. runs `campaign.py` and writes `results/` (`summary.tsv`, `shuffle.tsv`,
   `dec.tsv`, `go.tsv`, `versions.txt`).

Every random choice of the harness is seeded. Verificatum sessions are
generated with vmn's own demo scripts with all random sources seeded
(`gen_session.sh`); IVXV's `provableDecrypt` uses its own randomness, so its
proofs are stored in `fixtures/` (`REGEN=1` regenerates them). Two complete
runs with the same seed (one from a fresh work directory: fresh clones and
builds) give byte-identical result tables; the generated proof files are
byte-identical too, and the only differing input is the per-party RSA
signature key that `vmni` writes into `protInfo.xml`, which no verification
reads.

## What is compared

| component | deployed oracle(s) | certified side |
|---|---|---|
| shuffle | `vmnv -shuffle`; IVXV auditor `Verifier` (MixerTool's default) and `ThreadedVerifier` (`--threaded`), driven by `IvxvShuffleDiff` with IVXV's own reader | `main.exe shuffle`: `verify_pos_ins` of `VerificatumIvxvIns.v` per key-width component |
| dec | IVXV `ElGamalDecryptionProof`, as the auditor's `DecryptTool` reads and verifies it (`IvxvDecDiff`) | `main.exe dec`: the Maurer verifier `verify_zkp_ins` of `SwissPostZkpIvxvIns.v`, IVXV's DPRNG challenge |
| go | IVXV Go core `PublicKey.Verify` (`tivi.io/core`, `go/main.go`) | `main.exe nizkp`: `SwissPostZkpIvxvGoIns.v`, SHAKE-256 challenge |

The certified instances are generated by `mkins.py` at the safe-prime group
of `group.txt` and at RFC 3526 group 14 (the Go library's group); the
primality of the groups is **assumed** (axioms), as in
`bench/swisspost-e2e/certified/mkins.py`. The certified Terelius–Wikström
verifier is stated for key width 1; for IVXV's key width 5 the trusted
driver checks every component j with the key (g, y_j), F'_j and k_F,j and the
challenges of the whole session (the equations A, B, C, D and k_E do not
depend on the key width). Arrays of G^κ elements are stored by Verificatum
as κ component arrays.

Sources of cases: honest proofs of the deployed provers; controls from our
independent provers (`ivxvlib.py`: a Terelius–Wikström prover and IVXV's
decryption proofs, Java and Go), including degenerate inputs (identity
permutation, no re-encryption, ciphertext component 1, plaintext 1, key 1);
Fiat–Shamir-consistent proofs of false statements from the same provers
(a map that is not a permutation, a wrong re-encryption exponent, a changed
plaintext, another shuffle, a decryption under another key, another salt);
field mutants by type (×g, 1, inverse, random; +1, 0, negated, random);
single-check isolation of each B equation (`k_B,i` changed); structural and
encoding mutants (lengths, non-canonical, non-reduced and negative
integers, values outside G_q, trailing data, metadata).

## Results (SEED=1)

See `results/summary.tsv`. Shuffles: 6 sessions (N = 2, 5, 10, 24 with one
mix-server and key width 5; N = 7 with two mix-servers; N = 5 with key width
1), 408 cases; decryption proofs: 424 cases; Go proofs: 184 cases. Every
honest proof and every control is accepted by every verifier, and every
proof of a false statement is rejected by every verifier. The disagreements
are listed, with their root causes, in the campaign report; in short:

- IVXV's default auditor shuffle verifier does not check the B equation at
  index 0 (`Verifier.verify_B` starts at 1); `ThreadedVerifier` does. A
  changed reply k_B,0 is accepted by the default mode only (8 cases).
- `vmnv -shuffle` exits 0 when proofs of shuffle fail and does not compare
  `ShuffledCiphertexts.bt` with the last party's output; its verdict is read
  from its output here.
- Encoding leniency: IVXV's shuffle reader (extra reply elements, a leading
  zero byte, replies outside [0, q), trailing data), IVXV's decryption proofs
  (non-reduced plaintext and announcement, response ± q, trailing data) and
  the Go core library (non-reduced and negative element encodings) accept
  inputs the certified verifiers reject at their boundary.
- Configuration: IVXV verifies only mix-server 01 and only key width 5, so
  a two-server session and a key-width-1 session are rejected by IVXV.
